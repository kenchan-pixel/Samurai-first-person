## Exact-head deployment verification

Use the strongest available signal in this order:

1. Direct Vercel deployment data that identifies the exact Git SHA.
2. GitHub commit status named `Vercel` for the exact current SHA.
3. **Build receipt fallback** only when the two integration signals above are unavailable/missing while the Preview alias itself is reachable: fetch `/build-meta.json` from the Preview alias and require its `commitSha` to equal the exact 40-character `autonomous-evolution` HEAD. When `branch` is available it must be `autonomous-evolution`.

The build receipt is generated by Vite from Vercel Git metadata (`VERCEL_GIT_COMMIT_SHA` / `VERCEL_GIT_COMMIT_REF`; Vite-prefixed equivalents are also accepted). It contains only build identity metadata and no secrets. `vercel.json` sends `Cache-Control: no-store` for the receipt to avoid certifying a stale alias response.

The receipt fallback is fail-closed:

- HTTP failure, missing receipt, `commitSha: unknown`, malformed/non-40-character SHA, branch mismatch, or SHA mismatch → Preview is **not** exact-head verified.
- An explicit Vercel failure status is never overridden by a receipt; diagnose/recover the failure under the normal blocker rules.
- A receipt proves the runtime served by the Preview alias belongs to the exact commit; it does not waive CI, review, regression, or browser-runtime gates.

## High-frequency usage rule

One real implementation/blocker-repair commit should normally produce one Preview update. Do not create multiple file-by-file commits or empty/log-only commits just to trigger Vercel. Every Preview should correspond to a meaningful repository state.

## Review gate

Preview deployment is allowed before review clearance because it is evidence used by reviewers. A blocker prevents **new feature work**, not Preview creation. Production remains gated by Ken merging `main`.
